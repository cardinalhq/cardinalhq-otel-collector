# fbn_auth extension

Server-side authenticator for self-signed bearer tokens. Intended for
receive paths where senders (e.g. freenet nodes) do not sign up individually;
their data lands in a shared tenant and is further validated by the
`fbn_validator` processor.

## Token format

Sent as `Authorization: Bearer <token>` where the token is:

```
prefix/base58(pubkey)/timestamp/base58(signature)
```

- `prefix` — must match a configured prefix (e.g. `freenet`)
- `pubkey` — base58-encoded public key (32 bytes); its type depends on the
  prefix's `signature_algo`
- `timestamp` — unix epoch seconds; must be within `max_clock_skew` of now
- `signature` — base58-encoded signature over the literal bytes of
  `prefix/base58(pubkey)/timestamp`

There is no nonce or salt field. A sender-chosen one would buy nothing here:
it is not replay protection unless the verifier tracks it, and it is not
precomputation resistance either, because the party who would precompute is
the same party who picks it. A token is therefore stable for a given
(key, second).

## Signature algorithms

- `xed25519` — what freenet nodes send. The pubkey is the sender's x25519
  (Montgomery) key — its actual network transport identity — and the
  signature is XEdDSA (Signal's construction). Verification converts the
  Montgomery key to an Edwards point (sign bit 0) and runs stock Ed25519
  verification; a cross-implementation vector generated by the freenet Rust
  signer is pinned in the tests.
- `ed25519` — the pubkey is a plain ed25519 verifying key and the signature
  is a standard Ed25519 signature.

Low-order public keys are rejected on both algorithms. `crypto/ed25519` is
not strict and would otherwise verify signatures against small-order keys,
which anyone can forge without holding a private key.

All verification is local (no network calls). Any parse or verification
failure denies the request — the extension fails closed. The denial reason
(`stale_timestamp`, `unknown_prefix`, `bad_signature`, …) is returned to the
sender so a misconfigured client is diagnosable from its own logs; the reasons
are coarse labels and never reveal key material.

On success the identity is attached to the request context as `client.AuthData`
with attributes `prefix`, `public_key`, `timestamp`, `signature`, and
`signature_algo`, for downstream consumption by `fbn_validator`.

## What this does and does not prove

It proves **possession of a private key** at a point in time. It is not an
access-control gate: there is no allowlist, so any sender with any valid
keypair authenticates successfully. What makes that useful is the
`fbn_validator` processor, which binds the payload to the key that
authenticated it.

**Tokens are replayable within the skew window.** Nothing tracks whether a
token has been seen before. A captured `Authorization` header can be reused
for up to `2 × max_clock_skew` (10 minutes at the default), and because the
signature covers only `prefix/pubkey/timestamp` and not the request body, a
replayed token can carry arbitrary telemetry attributed to that sender. TLS on
the receive path is what prevents capture. Lower `max_clock_skew` to narrow
the window; a bounded seen-set keyed on `(public_key, timestamp)` with a
`2 × max_clock_skew` TTL is what would close it — that pair is already unique
per sender per second, which is why dropping the uniqueness field costs
nothing here.

## Telemetry

- `auth_attempts` (counter) — one per authentication attempt, with a `result`
  attribute: `ok`, `no_header`, `malformed`, `unknown_prefix`, `bad_timestamp`,
  `stale_timestamp`, `bad_pubkey`, `bad_key_size`, `low_order_key`,
  `bad_signature`, or `bad_algo`.

## Configuration

```yaml
extensions:
  fbn_auth:
    max_clock_skew: 5m   # optional, default 5m; must be positive
    prefixes:
      freenet:
        signature_algo: xed25519   # what freenet nodes send; ed25519 also supported
```

Rotate to a new prefix if the signature algorithm for a sender population
needs to change.
